# Cape Customization

망토를 염색약으로 물들이고, 나중에는 유저가 올린 텍스처를 입힌다. 색과
텍스처는 **아이템 인스턴스에 붙고**, 주변 플레이어·캐릭터 선택 화면에서도
똑같이 보인다.

두 단계로 나눠 만든다.

| 단계 | 아이템 | 하는 일 | 상태 |
| ---- | ------ | ------- | ---- |
| 1 | Cape Dye | 색을 골라 착용한 망토를 염색 | 구현됨 |
| 2 | Cape Transfer Kit | 이미지를 올려 망토 텍스처 교체 | 구현됨 |

## 현재 구조

- 망토는 `items.csv`의 `capeColor`가 있는 back 슬롯 아이템이다. 색의 존재
  자체가 "이건 망토다"라는 판정이며, back 슬롯의 화살통 같은 미래 아이템은
  색이 없어 천이 되지 않는다 ([client/src/lib/data/itemDefs.ts](../client/src/lib/data/itemDefs.ts)).
- 천은 모델이 아니라 절차적 스킨드 메시다
  ([client/src/lib/effects/cape-rig.ts](../client/src/lib/effects/cape-rig.ts)).
  머티리얼은 색 문자열을 키로 한 전역 캐시에 공유된다.
- 남에게 보이는 경로는 def id 하나뿐이다: `Player.back`,
  `ServerMessage::PlayerBackChanged`, 캐릭터 선택의 `VisibleEquipment.back`.

즉 지금은 **아이템 종류당 색 하나**다. 인스턴스별 색이 들어가려면 저 세 경로가
전부 색을 함께 실어야 한다.

## 상태를 어디에 두는가

`enchant`와 똑같이 **아이템 인스턴스에** 둔다. 캐릭터에 두면 망토를 두 벌
가진 유저가 벗었다 입을 때마다 색이 뒤바뀌고, 염색한 망토를 거래·판매할 수
없다. 인스턴스에 두면 떨어뜨렸다 주워도, 남에게 넘겨도 색이 따라간다 —
`enchant`가 이미 그렇게 동작하므로 손댈 자리도 같다.

```rust
pub struct ItemInstance {
    pub instance_id: u64,
    pub item_def_id: String,
    pub quantity: u32,
    #[serde(default)]
    pub enchant: i32,
    /// 염색한 천 색(`#rrggbb`). 없으면 def의 `capeColor`.
    #[serde(default)]
    pub cape_color: Option<String>,
    /// 입힌 텍스처의 콘텐츠 해시. 2단계.
    #[serde(default)]
    pub cape_texture: Option<String>,
}
```

`enchant`가 지나간 자리를 그대로 따라간다.

| 자리 | 파일 | 한 일 |
| ---- | ---- | ----- |
| 인스턴스 | [shared/src/inventory.rs](../shared/src/inventory.rs) | 필드 2개 |
| 저장 | [server/src/auth.rs](../server/src/auth.rs) `ensure_character_item_columns` | 컬럼 2개 (`enchant` 추가 방식 그대로) |
| 바닥 | `GroundItem` | 드랍/줍기가 색을 지우지 않게 |
| 거래·상점 | `player_trade.rs`, `trading.rs` | 인챈트가 지나가는 자리마다 색도 함께 — 유저 거래, 상인 판매, 되사기(`BuybackEntry`), 주민 재고 |
| 방송 | `Player.back`, `PlayerBackChanged` | def id 옆에 색/텍스처 |
| 방송 비교 | `set_player_gear` ([player.rs](../server/src/game_state/player.rs)) | **def id만 비교하면 염색이 방송되지 않는다** — 염색은 def id를 바꾸지 않으므로 색/텍스처도 비교에 넣는다 |
| 선택 화면 | `VisibleEquipment`, `read_visible_equipment` | SELECT에 컬럼 추가 |

클라이언트에서 `capeColorOf(defId)`는 **판정용으로 남긴다**. 인스턴스 색은
그 위에 덮어쓰는 값이지, 망토냐 아니냐를 정하지 않는다.

메시지에 필드가 늘어나므로 `PROTOCOL_VERSION`을 올린다. 새 필드는 전부
`#[serde(default)]`라 저장된 옛 인벤토리 JSON은 그대로 읽힌다.

## 1단계 — 염색약

### 아이템

| 항목 | 값 |
| ---- | -- |
| id | `cape_dye` |
| category | `cape_dye` |
| basePrice | 800c (Wool Cape 4,000c의 20%) |
| weight | 0.5 |
| stackable | true |
| consumable | true (부팅 검사가 `UseEffect`와 짝을 강제한다) |
| 판매 | Rica (`data-src/merchants.csv` 카탈로그에 추가) |
| 아이콘 | `objects/cape_dye.png` — 제작 후 `doc/assets/items.md`에 출처 기록 |

색은 자유 선택이다. 팔레트를 고정하면 병 종류를 색마다 만들어야 하고, 유저가
직접 색을 고르는 것이 이 아이템의 전부다.

### 쓰는 규칙

ENCHANT와 같은 뼈대다.

- 전투불능 상태에서는 쓰지 못한다 — 소모하지 않고 거부한다.
- **망토를 착용하고 있지 않으면** 소모하지 않고 거부한다. 대상은 back 슬롯에
  착용한, `capeColor`를 가진 아이템 하나뿐이다. 가방 안의 망토는 대상이 아니다.
- 색을 확정해야 소모된다. 색 선택 창을 닫으면 아무 일도 없다.
- 몇 번이든 다시 염색할 수 있다. 마지막 색이 남는다.

### 흐름

서버에 "염색 대기" 상태를 두지 않는다. 대기 상태는 접속이 끊기거나 그 사이에
망토를 벗으면 정리해야 하는 쓰레기가 된다. 대신 사용은 평범한 `UseItem`이고,
**서버는 창을 열라고 답만 할 뿐 아무것도 소모하지 않는다.**

1. 가방에서 염색약 사용 → `ClientMessage::UseItem`. 가방·퀵슬롯·agent-client가
   모두 같은 메시지를 보내므로 "어떤 아이템이 창을 여는가"를 클라이언트가
   따로 알 필요가 없다.
2. 서버의 `UseEffect::PromptCapeDye`가 전투불능 여부와 망토 착용을 확인하고
   `ServerMessage::CapeDyePrompt { instance_id }`로 답한다. 거절도 여기서
   난다 — 색을 다 고른 뒤에 "망토가 없다"는 말을 듣는 일이 없다.
3. 클라이언트가 색 선택 창을 열고, 유저가 색을 확정 →
   `ClientMessage::DyeCape { instance_id, color }`.
4. 서버가 **다시 전부 검사한다**: 염색약이 아직 가방에 있는지, 전투불능 아님,
   back 슬롯에 망토 착용, `color`가 `#rrggbb` 형식. 창을 띄워 둔 시간은
   무한하고 그 사이에 망토를 벗거나 염색약을 넘길 수 있다.
5. 통과하면 망토 인스턴스의 `cape_color`를 바꾸고 염색약 1개를 소모한다.
   인벤토리 스냅샷과 `PlayerBackChanged`가 나간다.

`instance_id`는 염색약 쪽이다 — 대상 망토는 서버가 착용 슬롯에서 찾는다.
색은 저장 전에 소문자 `#rrggbb`로 정규화한다. `#FF0000`과 `#ff0000`이 따로
돌면 방송 비교가 헛돌고 클라이언트 머티리얼 캐시가 두 벌로 늘어난다.

`item_defs.rs`의 부팅 검사가 `consumable == use_effect().is_some()`를
강제하므로 `consumable=true`인 염색약은 어차피 `UseEffect` 변형이 하나
있어야 한다.

### 색 선택 창

- HTML `<input type="color">` 기반. 브라우저 기본 피커라 만들 것이 없다.
- 미리 정한 색 견본 몇 개를 함께 둔다 — 대부분은 견본에서 고르고, 자유
  선택은 원하는 유저용이다.
- 확정 전에 착용 중인 망토에 색을 실시간으로 반영한다. 내 화면에서 내 망토만
  바뀌며, 염색약 소모·서버 반영·타 유저 노출은 Dye를 눌러야 일어난다.
  취소하면 되돌린다.
- **창은 화면 왼쪽에 붙이고 배경을 어둡게 덮지 않는다.** 가운데 띄우면 미리
  보라고 만든 망토를 창이 그대로 가린다. 오른쪽은 염색약을 꺼낸 인벤토리가
  차지한다.

### 렌더링

머티리얼 캐시가 색 문자열로 키를 잡고 있어 인스턴스 색은 그대로 얹힌다.
다만 캐시에 상한이 없었다 — 자유 색이면 화면을 스쳐간 색 수만큼 머티리얼이
영원히 쌓인다. **입은 사람 수를 세도록** 바꿨다: 같은 색은 여럿이 공유하고,
마지막 한 명이 벗는 순간 dispose한다. 상한 상수도 청소 스캔도 필요 없고,
캐시 크기는 정확히 "지금 화면에 있는 색 수"다.

색을 바꿀 때 천을 다시 만들지 않는다. `CapeRig.setSkin`이 머티리얼만
갈아 끼운다 — 색 선택 창은 드래그하는 동안 색을 연속으로 던지고, 그때마다
스켈레톤을 새로 만들면 천이 매 프레임 정지 자세로 되돌아간다. 천 지오메트리와
스킨은 그대로 공유되므로 드로우콜은 늘지 않는다.

바닥에 떨어진 망토는 예외다. 드랍은 절차적 천이 아니라 GLB 모델
(`wool_cape.glb`)이라 염색색이 아니라 모델 색으로 보인다. 색 자체는
`GroundItem`이 들고 있으므로 주우면 되살아난다.

## 2단계 — 텍스처 교체

### 아이템

| 항목 | 값 |
| ---- | -- |
| id | `cape_transfer_kit` |
| category | `cape_texture` |
| basePrice | 5,000c (염색보다 비싸다 — 저장 용량을 쓴다) |
| weight | 0.5 |
| stackable | true |
| consumable | true — `UseEffect::PromptCapeTexture`(파일 선택 창을 열라는 응답만) |
| 판매 | Rica |
| 아이콘 | `objects/cape_transfer_kit.png` — `doc/assets/items.md`에 출처 기록 |

### 흐름

1. 가방에서 사용 → `UseEffect::PromptCapeTexture`가 전투불능과 망토 착용을
   확인하고 `ServerMessage::CapeTexturePrompt { instance_id }`로 답한다.
   1단계와 같은 이유로 서버는 대기 상태를 두지 않는다.
2. 클라이언트가 그림 선택 창을 연다. 고른 이미지는 캔버스에서 **높이를 정사각
   변에 맞추고 가운데 정렬**한 뒤 잘라 PNG로 다시 인코딩한다. 변은
   `min(512, 원본 높이)` — 작은 그림을 512로 늘리지 않는다. 늘려 봐야 샘플러가
   공짜로 해 줄 일을 픽셀로 저장해 모든 관람자에게 전송하는 것뿐이다. 여기서
   EXIF와 원본 용량도 사라진다. 세로가 잘리는 일은 없고, 가로로 넓은 그림만
   양옆이 잘린다. 어디에 얼마나 크게 앉는지는 천이 정한다(아래 "천에 UV
   입히기"). 원본보다 좁은 그림은 좌우에 투명 여백이 남고, 거기는 염색색이다.
3. `POST /api/cape-texture` — 본문은 PNG 그대로(multipart 불필요), 인증은
   아래의 업로드 토큰. 서버는 다음을 한다.
   - 크기 상한(512², 본문 2MB) 검사, 서버에서 **다시 디코드·재인코딩** —
     이미지가 아닌 것과 껍데기 안에 숨긴 것을 여기서 떨군다. 본문 상한이
     넉넉한 것은 PNG가 무손실이기 때문이다: 사진을 512²로 줄여도 300~600KB고,
     압축이 안 되는 것은 원본 픽셀 크기인 1MB에 가까워진다. 저장·전송량을
     실제로 묶는 것은 **변 길이 512²**지 본문 상한이 아니다.
   - 치수는 **헤더에서** 보고 거절한다. 압축된 바이트 수는 픽셀 수에 대해
     아무 말도 하지 않아서, 디코드부터 하고 재면 작은 파일이 큰 버퍼를 쓴 뒤에
     버려진다. 디코더에도 `Limits`를 걸어 512²+여유(4MB) 이상은 할당하지
     못하게 한다 — `image`의 기본 허용치는 512MB다.
   - 알파 경계 번짐(bleed) 처리.
   - 내용 해시로 파일 이름을 정한다(`<sha256>.png`). 같은 그림을 여러 명이
     올려도 파일은 하나다.
   - 계정당 업로드 빈도 제한(10분에 10장).
4. 응답의 해시로 `ClientMessage::ApplyCapeTexture { instance_id, texture }`.
   서버가 **해시를 저장소에 되물어 확인하고**(형식·존재·차단 여부) 키트를
   소모한 뒤 망토 인스턴스의 `cape_texture`를 설정한다. 이 확인이 없으면
   클라이언트가 아무 문자열이나 실어 보내고 주변 클라이언트가 그것을 URL로
   만든다.
5. 주변 클라이언트는 `PlayerBackChanged`의 해시로 `/api/cape-texture/<hash>`를
   받아 캐시한다.

파일은 하우징·터레인과 같은 디스크 경로(`<state_dir>/cape-textures`)에 두고
정적으로 서빙한다. 별도 스토리지를 붙이지 않는다.

#### 업로드는 왜 별도 토큰을 쓰나

클라이언트가 이미 들고 있는 `apiAuthToken`은 로그인할 때 받은 구글 ID
토큰이고, **한 시간이면 만료된다**. 게임 세션은 저녁 내내 이어지므로 두
시간째 플레이하던 사람의 업로드는 401로 떨어진다. 게다가 그 토큰은 관리자
허용목록을 검사하는 REST 쓰기용이라, 일반 플레이어의 쓰기를 그 경로에 태울
수도 없다.

그래서 서버가 인증 직후 `AuthSuccess`에 **업로드 토큰**을 실어 보낸다.
연결이 살아 있는 동안만 유효하고 연결이 끊기면 지워지므로 만료 스윕이 없다
(`CapeTextureStore::open_session` / `close_session`). 라우터는
`require_admin_for_writes` 레이어 **뒤에** merge해서 관리자 검사를 비켜간다.

#### URL에 확장자를 붙이지 않는 이유

prod nginx는 `location ~* \.(…|png|…)$`로 정적 번들을 서빙한다. 정규식
location은 접두사 `location /api/`를 이기므로 `/api/cape-texture/<hash>.png`는
백엔드에 닿지 못하고 404가 난다. 확장자 없는 경로는 그 규칙에 걸리지 않는다.

#### 캐싱은 하루, `immutable`은 안 쓴다

해시가 곧 내용이라 캐시된 사본이 **틀릴** 일은 없다. 그래서 `immutable` + 1년이
공짜처럼 보이지만, 그러면 **차단이 듣지 않는다** — 이미 받아 간 브라우저는 다시
묻지도 않으므로 차단된 그림을 1년 동안 계속 보여준다. `max-age=86400`은
군중의 fan-out을 막으면서 차단이 화면에서 사라지는 시간을 하루로 묶는다.

nginx도 `/api/cape-texture/`에 `proxy_cache`를 건다(`docker/nginx.conf.template`).
콘텐츠 주소라 안전하고, `proxy_cache_lock`으로 한 무리가 동시에 도착해도
업스트림 읽기는 그림당 한 번이다. GET·HEAD만 캐시되므로 업로드와 관리자 차단은
그대로 지나간다.

### 천에 UV 입히기

절차적 천 격자는 이미 `(u, 1-v)`를 UV로 싣고 있었지만, 그대로 두면 **정사각
텍스처가 세로로 2배 늘어난다**. 천은 폭보다 훨씬 긴 시트다 — 실측하면 knight
0.48, female_knight 0.41, barbarian 0.62 (평균폭/길이).

그래서 UV를 `((u-0.5)·printCrop + 0.5, 1-v)`로 바꿨다. 그림은 칼라에서
밑단까지 **세로로 꽉 차고**, 천은 그 폭의 가운데 `printCrop`만 보여주며
좌우를 잘라낸다. 올린 모양 그대로 붙고, UV가 `[0,1]`을 벗어나지 않으므로
샘플링이 clamp되는 일이 없다 — 가장자리까지 꽉 찬 그림도 바깥 열이 망토에
번지지 않는다.

칼라가 등에 파묻히는(`COLLAR_BIAS`) 만큼 위아래를 비워 둘까 했지만, 실제로
넣어 보니 0.01만 줘도 망토 끝에 염색색 띠가 보인다. 시트의 양 끝은 그대로
보이고 있었다는 뜻이라 여백은 두지 않는다.

#### 저장은 320×512

천은 폭의 `printCrop`(0.41~0.62)만 샘플링한다. 정사각으로 저장하면 **어느
착용자에게도 보이지 않는 픽셀이 1/3 이상** 전송되고 디코드되고 VRAM에 앉는다.
그래서 가장 넓은 rig보다 살짝 넓은 `320/512`를 저장 비율로 고정하고, UV는
`printCrop / PRINT_ASPECT`로 되읽는다. 100명이 각자 다른 그림을 입은 자리에서
전송 ~1.7GB, 클라당 VRAM ~50MiB가 사라진다.

`PRINT_ASPECT`를 바꾸면 **이미 저장된 그림이 잘못된 폭으로 그려진다** — 비율이
지오메트리에 구워져 있고, 그것이 크롭을 rig별로 공짜로 만드는 대가다. 텍스처마다
다른 비율을 허용하려면 크롭이 (rig × 텍스처)별이 되어야 하는데, 그러면 머티리얼·
텍스처 캐시 키에 rig가 들어가 군중 공유가 깨진다.

**보정을 파일이 아니라 천에서 하는 이유** 둘. 하나, `printCrop`은 rig마다
0.41~0.62로 다른데 파일은 내용 해시로 여러 사람이 공유한다 — knight 기준으로
눌러 저장하면 barbarian이 같은 그림을 입었을 때 다시 틀어진다. 둘, 값을 만질
때마다 **이미 올라간 그림이 전부 다시 놓인다** — 재업로드를 요구하지 않는다.
지오메트리 캐시 키에는 이미 폭·길이가 들어 있어 rig별 UV는 공짜다.

캐시는 **두 층**이 된다. 머티리얼은 `색|텍스처 URL`로, 텍스처는 **URL만으로**
따로 참조를 센다. 같은 그림을 다른 색으로 입은 두 사람은 머티리얼은 둘,
디코드와 GPU 텍스처(512² RGBA = 1MB)는 하나다 — 한 층이었다면 유행하는 문장
하나가 색 수만큼 디코드됐을 것이다. 마지막 한 명이 벗으면 둘 다 dispose된다.

`CapeSkin.texture`가 해시가 아니라 **URL**인 것은 의도적이다 — 선택 창이 아직
업로드하지 않은 로컬 파일을 같은 경로로 입혀 볼 수 있다.

### 색과 텍스처의 관계

**겹친다.** 염색한 색이 바탕이고, 텍스처는 알파가 있는 곳만 그 위를 덮는다.
천 머티리얼이 `MeshStandardNodeMaterial`이라 합성은 한 줄이다.

```ts
material.colorNode = mix(color(dye), print.rgb, print.a.mul(float(frontFacing)))
```

투명 PNG를 올리면 문양만 얹히고 나머지는 염색한 색 그대로다 — 바탕색은
염색약으로 갈아 끼우고 문장(紋章)은 텍스처로 다는, 예측 가능한 조합이 된다.
색을 곱하는 방식(어두운 색을 고르면 그림이 사라진다)과는 다르다.

어려운 길이 아니다. 머티리얼은 **여전히 불투명**하다(`transparent=false`).
비싼 것은 진짜 반투명 렌더링(정렬·depthWrite·그림자)이지, 셰이더 안에서 색을
섞는 것이 아니다. 늘어나는 비용은 텍스처 샘플 1회 + `mix` 1회고 드로우콜도
정렬 부담도 그대로다.

주의할 것 다섯.

- 텍스처는 `colorSpace = SRGBColorSpace`로 읽는다. 빼먹으면 그림 부분만 색이 뜬다.
- **로드는 비동기다.** 머티리얼은 염색색만으로 먼저 만들고, 그림이 도착하면
  `colorNode`를 붙인다. 차단당한 해시는 서빙되지 않으므로 로드가 그냥 실패하고
  망토는 염색색으로 남는다 — 차단이 곧 원상복구라, 인스턴스를 훑어 지우는
  일괄 작업이 필요 없다.
- **알파 경계의 검은 테두리**: 투명 픽셀의 RGB가 검정으로 저장된 PNG가 흔하고,
  그대로 섞으면 문양 가장자리에 검은 띠가 생긴다. 서버 재인코딩 단계에서
  가장자리 색을 투명 영역으로 번지게(alpha bleed) 처리한다.
- 머티리얼 캐시 키가 `색|텍스처 URL`이라 조합이 곱해진다. 비싼 쪽(텍스처)은
  URL만으로 따로 세므로 곱해지는 것은 머티리얼 객체뿐이다.
- 천은 `DoubleSide`다. 뒷면은 그림이 뒤집혀 보이므로 `frontFacing`으로 갈라
  **안감은 염색색만** 쓴다.

### 스테이지 2에서 조용히 틀릴 자리

`cape_texture`를 추가하면 구조체 필드는 컴파일러가 다 잡아 주지만, **동등
비교 세 곳은 에러 없이 틀린다**: `stack_into_bag`의 스택 병합 조건,
`player_trade.rs`의 "제시한 물건이 그대로인가" 재검증, 그리고
`set_player_gear`의 방송 비교다. 셋 다 def id·인챈트·색을 하나씩 나열해
비교하므로, 텍스처만 다른 망토가 같은 것으로 통과한다. 앞의 둘은
`prints_keep_otherwise_identical_capes_apart`가, 마지막은
`a_print_reaches_nearby_players`가 잡는다.

### 유해물 대응

올린 그림은 근처의 모든 유저에게 보인다. 검열 없이 열면 언젠가 반드시 문제가
된다. 처음부터 아래를 함께 넣는다.

- **신고**: 상대를 우클릭 → "Report cape". 신고는 해시·신고자·대상을 남긴다.
  플레이어 우클릭은 전용 레이캐스트(`inputHandler.pickPlayer`)로 잡는다 —
  플레이어를 기존 클릭 인텐트에 넣으면 지나가는 사람을 좌클릭할 때마다
  상호작용이 걸린다.
- **관리자 삭제**: `POST /api/cape-texture/<hash>/block` (기존 관리자
  미들웨어 뒤). 차단된 해시는 서빙되지 않고 파일이 지워지며, 그 해시를 쓰던
  모든 망토가 염색색으로 돌아간다. 같은 그림을 다시 올려도 해시가 같으므로
  재업로드가 막힌다.
- 차단 목록과 신고는 `<state_dir>/cape-textures/blocked`,
  `reports.jsonl` 두 파일이다. 관리자 규모의 양이라 DB 테이블과 마이그레이션을
  붙일 이유가 없다.
- **되돌리기 비용 없음**: 삭제당한 유저에게 키트를 돌려주지 않는다.
- 자동 이미지 판별은 넣지 않는다. 신고 + 해시 차단으로 시작하고, 신고량이
  감당이 안 될 때 다시 본다.
