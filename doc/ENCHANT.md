# Enchant System

드랍 전용 주문서를 읽어 장비를 +1 강화한다. 확정 구간을 넘기면 실패 시
장비가 파괴되는 리니지식 도전이며, 설계 의도(내구도 대신 자발적 싱크)는
[DESIGN_DIRECTION.md](DESIGN_DIRECTION.md)의 "싱크는 인챈트 도전으로"에 있다.

주문서는 두 종류다.

| 주문서 | 대상 | +N 효과 | 카테고리 | 가격 | 월드 드랍 |
| ------ | ---- | ------- | -------- | ---: | --------: |
| Scroll of Enchant Weapon | 장착한 주무기 | 명중·피해 굴림에 +N | `enchant_scroll` | 1,200c | 1% |
| Scroll of Enchant Armor | 착용 방어구 중 **무작위 1개** | guard에 +N | `enchant_armor_scroll` | 1,200c | 1% |

- 정의: [data-src/items.csv](../data-src/items.csv), 드랍률: [data-src/world_drop.csv](../data-src/world_drop.csv)
- 상인은 팔지 않는다. 획득 경로는 월드 드랍뿐이고, 되팔기는 가능하다.

## 읽는 규칙

공통:

- 전투불능 상태에서는 읽지 못한다 — 주문서를 소모하지 않고 거부한다.
- 대상이 없으면(무기 미장착 / 방어구 미착용) 역시 소모하지 않고 거부한다.
- 대상이 있으면 **성공하든 파괴되든 주문서는 소모된다.**
- 확률 굴림은 서버가 잠금 밖에서 하고, 결과는 인벤토리 스냅샷과 갱신된
  guard로 클라이언트에 함께 내려간다.

방어구 전용:

- 대상은 `category=armor`인 착용 아이템 중 하나를 균등 확률로 고른다.
  투구·갑옷·방패·장갑·바지·신발이 해당한다.
- 무기와 액세서리(반지·목걸이·벨트)는 대상이 아니다. `ring_of_protection`은
  guard를 주지만 `accessory`라 강화되지 않는다.
- 읽는 순간 착용 중인 것만 후보다. 벗어 두면 대상에서 빠지므로 사실상
  지정이 가능하다 — 아래 "무작위 대상의 실제 의미" 참고.

## 확률 사다리

무기는 +4까지, 방어구는 +2까지 확정이다. 그 위로는 같은 곡선
(75/50/25% → 이후 반감 → 1% 바닥)을 쓰되 방어구가 두 칸 아래에서 시작한다
— 방어구는 부위가 6개라 무기 한 자루와 같은 확정 구간을 주면 총 guard
증가폭이 6배가 되기 때문이다.

| 현재 → 다음 | 무기 성공률 | 방어구 성공률 |
| ----------- | ----------: | ------------: |
| +0 → +1     |        100% |          100% |
| +1 → +2     |        100% |          100% |
| +2 → +3     |        100% |          100% |
| +3 → +4     |        100% |       **75%** |
| +4 → +5     |        100% |           50% |
| +5 → +6     |     **75%** |           25% |
| +6 → +7     |         50% |         12.5% |
| +7 → +8     |         25% |         6.25% |
| +8 → +9     |       12.5% |         3.12% |
| +9 → +10    |       6.25% |         1.56% |
| +10 → +11   |       3.12% |     1% (바닥) |
| +11 → +12   |       1.56% |            1% |
| +12 이상    |   1% (바닥) |            1% |

실패하면 확률표의 나머지가 그대로 파괴 확률이다. 사다리는 1%에서 멈추고
더 닫히지 않는다 — 이론상 상한은 없고 비용만 폭발한다.

- 구현: [`enchant_success_bp`](../server/src/game_state/inventory.rs) /
  `armor_enchant_success_bp`(= 무기 사다리를 두 칸 밀어 재사용)

## 기대 소모량

실패 시 베이스 아이템까지 잃고 +0부터 다시 시작한다는 전제의 기대값이다.
점화식은 `E[아이템](N) = E[아이템](N-1) / p_N`,
`E[주문서](N) = (E[주문서](N-1) + 1) / p_N`.

무기:

| 목표 | 마지막 단계 성공률 | 기대 베이스 무기 | 기대 주문서 |
| ---- | -----------------: | ---------------: | ----------: |
| +5   |               100% |                1 |           5 |
| +6   |                75% |              1.3 |           8 |
| +7   |                50% |              2.7 |          18 |
| +8   |                25% |             10.7 |          76 |
| +9   |              12.5% |             85.3 |         616 |
| +10  |              6.25% |            1,365 |       9,872 |
| +11  |              3.12% |           43,761 |     316,442 |
| +12  |              1.56% |        2,805,172 |  20,284,827 |

방어구(부위 하나 기준):

| 목표 | 마지막 단계 성공률 | 기대 베이스 방어구 | 기대 주문서 |
| ---- | -----------------: | -----------------: | ----------: |
| +3   |               100% |                  1 |           3 |
| +4   |                75% |                1.3 |           5 |
| +5   |                50% |                2.7 |          13 |
| +6   |                25% |               10.7 |          55 |
| +7   |              12.5% |               85.3 |         445 |
| +8   |              6.25% |              1,365 |       7,141 |
| +9   |              3.12% |             43,761 |     228,921 |
| +10  |              1.56% |          2,805,172 |  14,674,483 |

무기 표는 DESIGN_DIRECTION.md의 라이브 커브와 동일하고, 방어구 표는
몬테카를로(2만 회)로 대조 확인했다.

읽는 방식이 다르므로 체감도 다르다. +0 방어구에 주문서를 계속 부으면
**평균 5.2장째에 파괴**되고 기대 도달치는 +4 언저리다(무기는 7.2장, +6
언저리). 현실적 상한은 방어구 +5(도달률 37.5%)~+6(9.4%), 무기
+7(37.5%)~+8(9.4%)이다.

## guard에 미치는 영향

방어구 +N은 착용 중인 동안 그대로 wearer의 guard에 더해진다. guard는 곧
공격자가 넘겨야 하는 명중 목표값이므로([COMBAT.md](COMBAT.md)), +1마다
그 캐릭터를 노리는 모든 공격의 명중률이 5%p(d20 한 칸) 내려간다. 공격자의
최대 굴림을 넘어선 뒤로는 폭발 주사위 구간이라 감소폭이 훨씬 가팔라진다
— guard 40이면 저레벨 몬스터 기준 0.25%다([COMBAT.md](COMBAT.md)).

- 계산: `effective_guard` = 기본 attr guard + Σ(장비 `guard` + 방어구 `enchant`)
  — [server/src/game_state/combat.rs](../server/src/game_state/combat.rs)의 `equipped_guard`
- 6부위를 모두 확정 구간(+3)까지 채우면 guard +18이다. 다만 드는 비용은
  운용에 따라 갈린다 — 아래 "무작위 대상의 실제 의미" 참고.
- 무기 +N은 guard에 관여하지 않는다. 반대로 방어구 +N은 명중·피해에 관여하지 않는다.

파괴되면 그 방어구는 장비창에서 사라지고 guard가 즉시 내려간다. 서버가
갱신된 스냅샷과 guard를 함께 밀어주므로 클라이언트가 재계산하지 않는다.

## 무작위 대상의 실제 의미

대상은 **읽는 시점에 착용 중인** 방어구 중에서만 뽑힌다. 즉 벗으면 대상에서
빠지므로, 플레이어는 강화하고 싶은 부위만 착용한 채 읽어 사실상 대상을 지정할
수 있다. 6부위를 +3까지 채우는 비용이 운용에 따라 이렇게 갈린다(시뮬레이션 2만 회):

| 운용 | 기대 주문서 | 기대 파괴 | 6부위 모두 생존 |
| ---- | ----------: | --------: | --------------: |
| 한 부위씩 착용하고 읽기 | 18 | 0 | 100% |
| 6부위 다 입은 채로 읽기 | 25.7 | 3.1 | 2.8% |

무작위 대상이 진짜 제약이 되는 구간은 확정 구간을 넘긴 뒤다 — 이미 +3인
부위가 뽑히면 25% 파괴를 감수해야 하므로, 다 입은 채로 계속 읽는 플레이는
평균 3부위를 잃는다. 반대로 벗고 읽는 플레이에게는 확정 구간이 온전히 확정이다.

이 우회를 막을지는 열린 설계 문제다. 막는다면 "착용 중인 방어구 전체가 아니라
슬롯 목록 전체에서 뽑는다"거나 "읽는 순간 6부위 착용을 요구한다" 같은 방향이
있고, 그대로 두면 "손이 가는 만큼 안전해진다"는 넷핵식 지식 보상이 된다.
현재는 후자다.

## 조정 손잡이

- **확정 구간**: `enchant_success_bp`의 `..=4`와 방어구 shift 값. 방어구를
  두 칸 민 이유는 부위 수 6개다 — 부위가 늘거나 줄면 이 값을 함께 본다.
- **공급**: `world_drop.csv`의 드랍률. 방어구는 부위 수만큼 수요가 크므로
  무기와 같은 1%로 시작해 텔레메트리를 보고 조정한다
  ([DESIGN_DIRECTION.md](DESIGN_DIRECTION.md)의 공급 확대 항목).
- **골드 싱크**: 시도마다 소모품(연마유 등)을 요구하는 설계가
  DESIGN_DIRECTION.md에 있으나 아직 구현하지 않았다. 확률표와 독립적으로
  소각량을 조절하는 손잡이다.
